# Architecture

TypeScript · Next.js 16 (App Router) · React Three Fiber · PostgreSQL (or embedded PGlite) · persistent job queue · supplier and payment adapters with simulators.

  creature/       word reels (identity as indices), powers, stats from bricks, worlds, reveal order, shuffle, Lab edit queue, sounds
  wishes.ts       wish codes, grown-up view, claims (frozen copies), kid status stages

## Single source of truth
`DesignModel.parts` (part id, color, x/y/z, rotation, component, step) is generated by deterministic code from bounded parameters. The 3D preview (`BrickViewer`), the step diagrams and PDF (`instructions/iso.ts`), the BOM and the exports all derive from it. Tests assert that BOM totals equal step callout totals. Colors do not change `structuralKey`; structural parameters do.

## Creature Lab data flow
- **Kid side** (`/lab`, `/lab/[id]`): a lab design is an ordinary design whose params are bounded module choices, colors and an `identity` (word-reel indices). Lab designs have no chat, uploads, rename, prices or exports, and `/design/[id]` redirects them to the Lab. Identity is not part of `structuralKey`, so renaming never changes the bricks.
- **Wish** (`POST /api/designs/[id]/wish`, table `wishes`, migration 002): freezes the current revision under a random code with a preset note id. No personal data.
- **Grown-up** (`/w`, `/w/[code]`): an age gate (nothing stored or sent) then the frozen creature, the fixed price and what arrives. "Order these bricks" calls `claimWish`, which copies the frozen revision into a new design owned by the grown-up's cookie and records it in `wish_claims` (migration 003). Each device gets its own copy; the first order wins, and the wish is ordered once. Claimed copies open on their checkout page, never in the Lab.
- **Order**: checkout accepts a lab design only if it is a claimed copy of an active wish, orders the frozen revision (never later edits), and quotes, authorizes and captures exactly `fixed_price_cents`. The kid's wish card polls `GET /api/wishes/[code]/status`, which answers only the cookie that owns the source design, with a forward-only stage (Ordered, Packing, On its way, It's here) and a calm "slow" flag for exceptions.
- **Creature Pack**: the order's PDF adds a cover with a serial, a cut-out card, a certificate with a blank "Builder" line and a final "Power up!" step.

## Order state machine
`draft → validating → quoting → awaiting_acceptance → payment_authorized → procuring → purchased → shipped → delivered`, with `exception`, `canceled` and `refunded`. Allowed transitions live in `orders/stateMachine.ts`. Every transition is written to `order_status_history` and `audit_events`. A holding exception records `held_from_status`, and resolution returns the order there or to an explicit target.

## Procurement safety
1. Re-run validation on the frozen model (never trust the stored result).
2. Quote and verify the exact lines: part, color, quantity, condition, stock, no extras, not expired.
3. Enforce the per-order limit and minimum contribution at quote time.
4. Customer accepts an active, unexpired quote. Authorization is idempotent per quote and method.
5. Before purchase: pause check, allowlist, authorization-window check, fresh re-quote compared with the accepted cost, per-order and daily limits, attempt limit.
6. Persist a `supplier_orders` row (`submitting`, unique idempotency key) **before** calling the supplier.
7. Ambiguous outcome → `uncertain` → reconcile by client reference (lookup twice before concluding "not placed"). Never retry blindly.
8. Partial fill → urgent exception with exposure. The customer is not charged. Cancel and compensate.
9. Capture only after confirmed procurement, never more than the accepted amount. Failures retry, then raise an urgent exception with exposure.
10. Tracking updates come only from querying the supplier. Webhooks merely trigger that query.
